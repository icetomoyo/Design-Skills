开始使用

LiteSync 给现有 SQLite 文件加一层 CRDT 合并：断网继续写，重连自动收敛

本地优先的同步引擎：一个 .db 文件多端读写，按行级操作合并、顺序确定可重放，不用改服务端，也不用改你的 schema。

为什么选 LiteSync，而不是再写一套同步脚本

合并语义

断网时照常写入，重连后按操作合并

LiteSync 记录行级操作，而不是整表快照。两台设备离线改同一行时按字段合并：A 改了状态、B 改了标题，两个修改都保留。不做 last-write-wins 覆盖，也不会把你的 UPDATE 变成别人的 DELETE。

设备 A · 离线UPDATE tasks SET status='doing' WHERE id=42
设备 B · 离线UPDATE tasks SET title='写规格' WHERE id=42
重连 · 自动合并status='doing' ∧ title='写规格' → 两字段同时生效，0 冲突

接入成本

接进现有 .db 文件，不改应用 schema

跑一次 litesync init：库里多一张 meta 表和两张触发器，你的表结构、外键、索引原样保留；不想要了，DROP 这三个对象即完全卸载。没有 daemon 常驻，同步跑在你应用的连接里。

$ litesync init --db app.db
created  litesync_meta          (1 张表)
created  trg_tasks_ins
created  trg_tasks_upd          (2 张触发器)

-- 检查：你的 schema 0 处变更
$ litesync doctor --db app.db
schema drift: none
tables touched by sync: tasks (opt-in)

可审计性

同步过程可审计、可重放

每次合并都追加写入 append-only 的 sync log（就是一张普通 SQLite 表），合并顺序由 (lamport, node_id) 确定性决定——同样输入永远得到同样结果。怀疑数据被改错时，用 litesync replay 在新库里逐步复现每一次收敛。

2026-11-22T09:14:02Z  op#1041  tasks#42  title  "write spec"   node=B
2026-11-22T09:14:02Z  op#1042  tasks#42  status "doing"        node=A
2026-11-22T09:14:03Z  merge   1041+1042 → fields(title,status)
2026-11-22T09:14:03Z  result  converged  conflicts=0  rows=2

$ litesync replay --log app.db --to 09:14:03 /tmp/verify.db
# 复现完成：与线上逐字节一致
