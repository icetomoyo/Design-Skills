Concord merges two offline SQLite writes into one row — inside the file itself.

A CRDT sync engine embedded as a SQLite extension. Every device writes plain SQL while offline; Concord merges contested columns deterministically and converges every replica to the same bytes. No server sits in the write path.

Same row, same column, two devices — both writes have a home.

Concord tracks every column as its own conflict-free register with a hybrid logical clock. A merge never loses a cell you didn’t contest, and a contested cell resolves by causality you can replay, not by which device happened to sync first.

Because the registers live in your SQLite file, the merge runs where your data runs: in-process, in a test, on a plane. There is no authoritative copy to reconcile against.

merge cost: O(columns touched) · no tombstone sweeps · zero network on write

The write path has no server in it.

Writes commit locally in microseconds; replication rides whatever bytes you already have. A WebSocket relay, WebRTC between peers, a shared folder, a mailed drive: Concord exchanges causal deltas, so the transport is dumb by design. A relay, when you want one for NAT traversal, forwards ciphertext it cannot read.

Merge order cannot change the result.

The merge is a pure function of causal history. Replay the same operations in any order, on any schedule, and every replica lands on the same bytes, so convergence becomes an assertion, not a hope.

Ship the assertion with your app: one command replays your fixtures through every permutation and fails the build the moment any two histories diverge.

determinism: pure merge · one hash per history · assertable in CI

Install the extension.

One package per runtime, or load the extension into any SQLite shell you already have. Your schema stays yours; Concord adds its registers per table.

Node · Electron 
npm install @concord/sqlite
Rust 
cargo add concord
Any SQLite shell 
.load libconcord
concord enable tasks;
